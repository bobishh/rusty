# Rusty

Repository: https://github.com/bobishh/rusty. Rusty pairs with tincanban as a storage and replication keeper. Its admin interface uses Fira Code for controls and content, Caveat for headings and the header wordmark, and Fira Code for identity details. Component styling and primitive paint come from the complete `src/styles/design-system/index.css` bundle in tincanban, pinned by `MATCH_UI_REV` in the Docker build; local development uses `MATCH_UI_SOURCE`. Rusty sets explicit font overrides in `frontend/src/typography.css`.

Rusty is Tincanban’s companion keeper: a little tin robot listening to several can telephones. Native Rust MetaMesh participant. It stores signed state for multiple Tincanban workspaces and synchronizes each scope over Iroh. Each scope and peer has its own retry loop, so an unreachable peer does not delay other boards.

Build the pinned Git dependencies:

```sh
cargo build --release --locked
```

Provision with a Tincanban owner-issued invitation:

```sh
mesh-lighthouse join INVITE_URL STATE_DIR
mesh-lighthouse STATE_DIR/config.json
```

In Tincanban, open **Sync → Add keeper**, select the starting boards, and generate an invitation. Keeper access requires an Editor invitation and a separately signed Editor grant for each selected board. The owner can explicitly enable **Connect all my boards, including future boards**. Rusty uses its own identity; it never receives the owner's private keys. Ordinary Visitor invitations keep their existing limited access.

Owner connection pins the approving person and service. Additional boards require a fresh owner-signed Editor grant, signed route, and verified Tincanban document before becoming active. Rusty records active scopes, grant epochs, future-board policy, and removal tombstones in its durable registry. Signed status lets another authorized owner device reconcile that registry; new future-board grants still require an owner device to be online. Removing a board first blocks its route, records a tombstone, then removes only that scope’s owned files and credentials. A cleanup failure stays pending and retries after restart; Rusty confirms removal only after cleanup completes. Re-adding a removed board requires a fresh pairing and newer signed grant.

Set `LIGHTHOUSE_TRACE_SYNC=1` to log frame types and service-lock timings when diagnosing slow replication. The trace omits frame payloads and invitation secrets.

`config.json`, scope state files, and `route-sequence` contain private identity or board state. Keep `STATE_DIR` private and durable. Existing single-scope configuration remains readable. JEV intake targets the unique replicated board with the `job-search` preset, including when it is not the primary invited board. If no such board exists or more than one matches, intake remains queued.

The HTTP intake runs independently before a mesh identity is paired:

```sh
mesh-lighthouse serve-http STATE_DIR 127.0.0.1:8080
curl -X POST -H 'Content-Type: application/json' \
  -d '{"message":"Hello","contact":"me@example.com"}' http://127.0.0.1:8080/ingest
```

`GET /challenge` issues a short-lived signed human check. `POST /ingest` verifies it, durably stores a bounded JSON message under `STATE_DIR/inbox`, and returns `202` with `status: pending`. A background worker classifies opportunity relevance, role type, and seniority with Jev, retaining every probability distribution. Once paired, every intake is posted to workspace chat; relevant opportunities also become idempotent Tincanban lead cards. `GET /health` supports the deploy proxy. When the native mesh process is paired, `LIGHTHOUSE_HTTP_BIND=0.0.0.0:8080 mesh-lighthouse STATE_DIR/config.json` serves and processes the same inbox alongside replication.

For Tincanban hostname discovery, set `LIGHTHOUSE_PUBLIC_ORIGIN` to the external HTTPS origin and `LIGHTHOUSE_CORS_ORIGINS` to a comma-separated allowlist of exact Tincanban web origins. HTTP origins are allowed only on loopback for development. No browser origins are allowed unless configured. `GET /.well-known/mesh-lighthouse` exposes the configured service identity and supported capabilities. Pairing requires the controller's signed approval and an authenticated operator decision bound to one transcript. After both approvals, Tincanban sends a signed Editor invitation and a separately verifiable board grant. Failed setup includes its bounded exact error in signed status and the operator view, and logs the full error on the server; Tincanban shows it beside the retry control. Rusty joins with its existing identity, verifies each selected board, stages all scopes, and activates them in one durable registry write. Tincanban reports active only after Rusty signs its committed per-board result. Signed `POST /v1/integrations/status` reports current scopes, grant epochs, and tombstones to the verified owner; response signature binds service identity, controller identity/device, and request operation ID. Signed `POST /v1/integrations/{integrationId}/disconnect` requires the current owner, expected integration revision, operation ID, and exact workspace/grant-epoch list. Rusty hashes canonical signed intent, records tombstones before cleanup, and returns a signed receipt bound to the current signing device. A valid current device for the same owner can resume the same operation with the same request hash. Changed intent conflicts. Pending cleanup remains visible in signed status until retry or restart completes it. Pairing receipts remain historical; signed status reflects current active scopes. A detached pairing cannot reactivate its old scope; re-adding requires a new approved pairing and a newer signed Editor grant. Discovery alone proves no prior service ownership and grants no board access. Operators can use **Settings → Reset keeper**, then re-enter the operator token. Reset drains the process and clears all active boards, pairing requests, intake messages, Jev results, and cached proof pages before restart. Service identity, route sequence, and allowed origins remain. A private recovery snapshot is retained under `STATE_DIR/reset-backups`; restoration requires stopping the service and operator access to its storage. Docker must retain its `unless-stopped` restart policy. A standalone process must be relaunched after reset. In Rusty’s admin Boards list, **Unsubscribe → Confirm unsubscribe** records a scoped tombstone, stops replication, and removes only that board’s stored replica and credentials after cleanup succeeds. Owners can detach their own boards; operators can detach any board. Detaching also ends that owner’s future-board subscription. Tincanban retains its local board. Re-adding uses separate storage and requires a fresh approved grant. Removing every board preserves Rusty’s service identity and historical pairing receipts.

For an initialized service, set `LIGHTHOUSE_ADMIN_TOKEN` to the operator secret, then open **Sync → Add keeper** in Tincanban. Enter the public hostname and discover the service. Tincanban selects all currently owned boards and **Also replicate my future boards** by default. The operator signs in at `/admin/`, compares the code and identities, and approves the displayed boards and future-board policy. The owner independently confirms the same code in Tincanban. Until both approve, no board access is granted.

The operator page keeps the Rusty service identity, its replicated boards, and the JEV intake trigger together under **Keepers**. Pairing requests stay under **Approvals**. The JEV row reports whether `JEV_API_KEY` is configured, pending intake count, and saved outcomes; intake targets the unique `job-search` board. Replication state reflects the native replication worker and active peers, not HTTP readiness. The page polls the authenticated `GET /admin/api/overview` and `/admin/api/pairings` endpoints every five seconds while visible, then refreshes when the tab becomes visible again. A failed poll leaves the last good overview visible and retries on the next interval. The endpoints return `403` without the operator session.

Activation stores each scope under `STATE_DIR/scopes/<activation hash>/state.json` before committing `config.json`. The completion receipt binds the exact offered snapshot, board list, and future-board policy. A lost HTTP response can be recovered through signed status or an exact retry after restart; a different snapshot cannot reuse the earlier commit. Failed activation remains pending and does not produce a durable ACK. New boards still require an online approving browser to issue signed grants.

For deployment, retain the existing durable volume and stop the old native process before starting its replacement: two processes must not write the same registry or use the same device identity concurrently. Build and deliver the new image before stopping the old process. Back up the complete stopped `STATE_DIR`, including `config.json`, `scopes`, the primary state, pairing records, and inbox. A health check confirms HTTP readiness; inspect discovery for pairing/provisioning capabilities separately. Restart with the same volume to recover committed scopes. If startup fails, stop the replacement and restart the previous image; retain the backup for recovery. Never restore only `config.json` without its referenced scope files.

The container starts in HTTP-only mode. An owner-issued invitation can initialize the existing `/data` volume without deleting its inbox. Restart the container after `join` succeeds; it then runs the native mesh peer and HTTP intake together. A failed join removes only its incomplete mesh state, leaving queued messages intact. Invite secrets must not be logged or committed.

`Cargo.toml` and `Cargo.lock` pin Tincanban authority and MetaMesh revisions so the node uses shared authority rules and Rust types. Tincanban’s `e2e/lighthouse-keeper-provisioning.spec.ts` runs against this standalone binary and checks discovery, operator login failure, pending and mutual approval, current and future boards, stable state files, lost HTTP responses, restart, exact retry, scoped removal, and signed status after restart. Its `lighthouse-join` scenario still exercises the in-tree adapter. Proof paging bounds transfer size but does not prune Automerge history; capacity and production connection stability need separate measurements.

The native keeper advertises `causal-write-admission-v1` for new and existing configs, and rejects incoming handshakes without it. Before acknowledging document exchange, the keeper verifies the signed authority snapshot and candidate change hashes through Tincanban authority admission. The keeper acts as a storage relay: unauthorized candidates fail as a whole and leave saved state unchanged. Tincanban owns raw-history quarantine and the authorized causal projection; the keeper does not retain or publish a separate quarantine view. Chat v2 records pass through as signed JSON. The keeper advertises `contextual-v2` only with the causal-capable native session and emits batch version 2 when stored messages contain signed v2 payloads.
